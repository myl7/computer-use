\section{Introduction}
\label{sec:intro}

Large language models have advanced rapidly.
This progress enables computer-use agents.
A computer-use agent interacts with applications through graphical user interfaces (GUIs).
At each step, the agent reads the GUI as both a screenshot and a structured text tree, e.g., an accessibility or DOM tree \citep{hong2024cogagent,zhang2025ufo}.
It then runs a ReAct-style \citep{yao2023react} agent loop, i.e., it calls the model to generate actions and executes them on the interface.
Task success rates keep rising on benchmarks of web, desktop, and mobile tasks \citep{xie2024osworld,rawles2025androidworld}.
However, computer-use agents consume more tokens than general agents because of the screenshot inputs, making them more expensive to run.
Token efficiency, i.e., reducing the token cost, has become a first-order concern.

To improve token efficiency, prior systems reuse earlier experience.
When an agent solves similar tasks repeatedly, starting from scratch repeats the discovery of the same procedure.
They reduce this cost by storing experience as text (e.g., memory items or skills) \citep{wang2025awm,zheng2024synapse}, or \textit{compiling} it into parameterized programs \citep{wang2025asi,li2026preact,chen2026autorpa,elyadouni2026tracecompiler}.
We focus on programs that remove model calls from the execution of the shared procedure.
After a model call that extracts the program inputs from the task prompt, the program executes the procedure without further model calls.

However, a low execution cost does not mean that compilation saves tokens over the full task stream.
Compiling a program is expensive and uncertain.
Creating and testing a program consumes tokens, and failed attempts produce no program.
A successful program saves tokens only if it serves enough tasks to recover this compilation cost.
Across published audits, this \emph{payback count} ranges from 4 uses \citep{chen2026autorpa} to 17 uses \citep{trooskens2026compiledai}, and most systems report no payback count \citep{elyadouni2026tracecompiler,xu2026skillsmith}.
These audits measure different costs and use different baselines, making their numbers incomparable.
We therefore ask: \emph{when is compilation worth its cost, and how can an agent decide from past observations, despite uncertain compilation costs and future uses, while bounding extra spending relative to continued agent service?}

Deciding when to compile faces two challenges.
\textbf{Random price.}
Before an attempt, the system does not know whether it will obtain a verified program or how many tokens it will spend.
Program repair adds model calls, and an attempt that fails verification still incurs its full cost without delivering a program.
Measuring only programs that pass verification leaves out this spend.
\textbf{Unknown arrivals.}
The system does not know how many tasks will arrive to recover this compilation cost.
Similar tasks may stop arriving before they pay back the spend, while changes to the GUI, or \emph{GUI drift}, can break a deployed program prematurely.
Compiling early can waste tokens if tasks do not repeat, whereas waiting can forgo savings on tasks that repeat often.
An online rule must make this choice using only past observations.

We introduce \emph{PACE} (Price-Aware Compilation from Experience), which combines a measurement protocol with an online compilation rule.
The measurement separates the cost of obtaining a program from the saving after that program exists.
The serving comparison uses matched task inputs and includes agent fallback after a detected program failure.
The protocol compiles recorded agent traces, selects programs through a validation gate, and charges the model calls on both successful and unsuccessful compilation paths.
Deployment runs measure extraction cost and program failures.
Additional compilations test whether the initial outcome repeats, and agent replays on the program's task inputs check the serving comparison.
Across seven task families and three models, the measurements show per-use savings alongside differences in compilation cost and outcome.

PACE uses this account to decide when to compile under a cumulative cost constraint.
A projected-savings rule uses past recurrence and verification outcomes to propose compilation.
A separate budget check admits an action only when its possible cost fits the allowance determined by the task arrivals already observed.
The account includes serving, routing, and every successful or failed compilation.
Under the stated cost model, PACE spends at most $1+\epsilon$ times an agent-only cost reference after every task arrival.
The margin $\epsilon$ limits the extra spend even when future-use estimates are wrong or compilation keeps failing.
We evaluate the resulting savings and tradeoffs with measured cost profiles, synthetic arrivals, and arrival orders from public logs.

\Needspace{4\baselineskip}
Our contributions are:
\begin{itemize}
\item A measurement protocol for the cost and saving of compiling computer-use tasks.
We report serving costs, compilation outcomes, repair costs, and payback counts under a shared accounting scheme, with repeated compilations and matched task-input replays.
\item An online protocol with an agent-relative cost bound.
PACE combines a reuse estimate with a budget based on costs already charged.
We prove a cumulative bound under action-cost assumptions.
\item An implementation and evaluation across cost and recurrence settings.
We retain the measurement records, policy implementations, and paired simulation outcomes.
With $\epsilon=0.25$, PACE's mean cost across twelve model--log conditions is $0.781$ of agent-only service, compared with $1.062$ and $0.995$ for decision-rule adaptations of AutoRPA and ToolPro.
Ablations separate the effects of the savings test, cost budget, and failed-attempt price.
\end{itemize}

\section{Related Work}
\label{sec:related}

Experience reuse includes executable skill libraries in Voyager \citep{wang2023voyager}, extracted trajectory insights in ExpeL \citep{zhao2023expel}, and procedural-skill refinement in Skill-Pro \citep{mi2026skillpro}.
LATM separates tool making from tool use to amortize creation cost across requests \citep{cai2023toolmakers}.
PACE studies the compilation spend, including unsuccessful attempts, and the online decision to incur it.
Prediction-guided rent-or-buy algorithms study purchase timing under uncertain future demand \citep{purohit2018improving,gollapudi2019online}, while conservative contextual bandits constrain cumulative performance relative to a baseline \citep{kazerouni2016conservative}.
PACE uses the latter type of constraint for token charges, with measured compilation profiles and reservations that remain valid when the reuse proposal is wrong.

\section{Limitations}
\label{sec:limitations}

The measurements cover seven parameterized task families and three model profiles.
Broader studies could include workflows that span several applications, longer procedures, and task descriptions with greater variation.
The current account focuses on model-token cost.
Adding latency, device use, and program-maintenance effort would support decisions that must satisfy several resource constraints.
Model and provider updates can change the measured costs, so periodic remeasurement would help assess how long a profile remains useful.
Experiments across longer deployment periods could also measure how maintenance effort grows as applications change.
Finally, the current implementation receives task-family labels from the workload.
Integrating a family-discovery component with the measured routing account would extend it to unlabeled task streams.
